# 01. Сопоставление заказов маркетплейса с выгрузкой 1С

CLI-проверка заказов перед передачей в 1С: сопоставляет позиции с номенклатурой,
ищет расхождения (нет артикула, другая цена, не хватает остатка, дубли), формирует
отчёт для менеджера и лог обработки. Скрипт не падает на одной битой записи.

## Требования и запуск

PHP 8.1+ (проверено на 8.4.27), внешних зависимостей и Composer нет.

Самый простой способ — из корня репозитория одной командой:

```cmd
run.cmd -Task 01
```

Скрипт сам найдёт PHP (если нет — скачает портативную сборку, если не указан
`-NoBootstrap`), прогонит `bugs/OrderTotal.php` и положит отчёты в `var\`,
не трогая папку задания.

Вручную из папки `01-orders-1c-sync`:

```bash
php bin/check-orders.php
```

Если PHP не установлен в системе, можно положить портативную сборку в
`../.tools/php` (каталог исключён из git) и запускать так:

```powershell
..\.tools\php\php.exe bin\check-orders.php
```

Параметры:

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `--orders=PATH` | `data/orders.json` | JSON-файл **или URL** с заказами |
| `--nomenclature=PATH` | `data/nomenclature_1c.csv` | выгрузка номенклатуры 1С |
| `--csv=PATH` | `output/report.csv` | CSV-отчёт для Excel |
| `--txt=PATH` | `output/report.txt` | тот же отчёт в текстовом виде |
| `--log=PATH` | `output/app.log` | лог обработки |
| `--help` | | справка |

Источник заказов заменяется на HTTP без правок кода:

```bash
php bin/check-orders.php --orders="https://api.market.example/orders?page=1"
```

Коды возврата: `0` — заблокированных заказов нет, `1` — есть заблокированные,
`2` — фатальная ошибка (нет файла, битый JSON и т.п.).

В консоли Windows для читаемого вывода: `chcp 65001`.

## Что получается на выходе

* `output/report.txt` — отчёт для менеджера: заказы сгруппированы по вердиктам
  (заблокированы → требуют проверки → пропущены → готовы). У каждой проблемы
  написано, что делать; у готовых с пометкой (например нормализованный артикул)
  пометка видна в этом же блоке, а не только в CSV.
* `output/report.csv` — то же в таблице: один заказ — одна или несколько строк
  (по строке на проблему). UTF-8 с BOM, разделитель `;`, десятичная запятая —
  открывается в русском Excel двойным щелчком.
* `output/app.log` — ход обработки, пропущенные строки, дубли, фатальные ошибки.

Вердикты:

| Вердикт | Значение |
|---|---|
| `ГОТОВ` | расхождений нет, можно передавать в 1С |
| `ПРОВЕРИТЬ` | есть коммерческие расхождения (цена, остаток, дубль, сумма) — решает менеджер |
| `ЗАБЛОКИРОВАН` | передавать нельзя: нет артикула, нет цены или пустой заказ |
| `ПРОПУЩЕН` | отменён или повторная запись выгрузки |

## Принятые решения

**Сопоставление.** Артикул нормализуется: обрезаются пробелы, схлопываются
внутренние, регистр приводится к верхнему (`" ts-1002"` → `TS-1002`). Сравнение
идёт по артикулу, а не по наименованию: названия на площадке и в 1С могут
отличаться.

**Дубль заказа** — запись с тем же `id`. Первый экземпляр обрабатывается,
остальные помечаются `ПРОПУЩЕН` и остаток не резервируют. Альтернатива —
сравнивать содержимое, но `id` маркетплейса и есть ключ идемпотентности.

**Дубль строки** — один и тот же артикул несколько раз внутри заказа
(MP-24017: `TS-1006` строками 1 и 3). Количества складываются в одну позицию,
в отчёт идёт предупреждение: иначе остаток проверялся бы по каждой строке
отдельно и недостача терялась бы.

**Отменённые заказы** не передаются в 1С и не резервируют остаток
(MP-24027). Это единственный статус, который пропускается полностью.

**Остатки считаются кумулятивно** — заказы обрабатываются в хронологическом
порядке (`created_at`, при равенстве — `id`), каждая позиция уменьшает свободный
остаток карточки 1С. Поэтому MP-24013 (`TS-1025`, 3 шт.) проходит, а MP-24021
(ещё 2 шт. при остатке 4) получает «не хватает 1». Если смотреть каждый заказ
отдельно, вторую нехватку не увидеть. В отчёте есть колонки «Остаток 1С» и
«Свободно до заказа», чтобы решение было понятным.

**Несколько карточек 1С с одним артикулом** (`TS-1017`: 00-00100112 по 1,85 и
00-00100900 по 4,35). Выбирается карточка с подходящей ценой и положительным
остатком, но заказ получает предупреждение — справочник надо чистить.

**Цена.** Расхождение более 0,005 — предупреждение `ПРОВЕРИТЬ`, а не блокировка:
это коммерческое решение (акция, старая цена). В отчёте видны обе цены и
разница в рублях и процентах.

**Блокируют передачу** только случаи, когда строку физически нельзя провести:
артикула нет в 1С, в строке нет цены, в заказе нет позиций.

**Сумма заказа** сверяется с суммой строк (допуск 0,005). Расхождение — повод
пересчитать, но не блокировка.

**Валюта.** Всё, кроме `BYN`, — предупреждение: цены 1С в задании в BYN.

**Битые записи.** Ошибка разбора заказа (нет `id`, плохая дата, нечисловое
количество) пишется в лог, в отчёт попадает строка `INVALID_RECORD`, остальные
заказы обрабатываются дальше. Битые строки номенклатуры точно так же
пропускаются с записью в лог.

## Исправленные баги в `bugs/OrderTotal.php`

1. **Цена обрезалась до целого** (`(int) $item['price']`). Из-за этого 3,20
   превращалось в 3, а 18,50 — в 18, и сумма заказа занижалась. Исправлено на
   `(float)`.
2. **НДС считался как 20 % от суммы** (`$total * 20 / 100`), хотя цена уже
   включает НДС. Правильная формула — `20 / 120`: НДС «внутри» суммы, иначе он
   завышается в 1,2 раза (382,98 вместо 319,15). Исправлено на
   `VAT_RATE / (100 + VAT_RATE)`.
3. **НДС брался от суммы до скидки** (`vatIncluded($subtotal)`), поэтому при
   скидке 10 % он не уменьшался (319,15 вместо 287,24). Теперь базой служит
   итог к оплате `$total`.

Самопроверка: `php bugs/OrderTotal.php` — «Все проверки пройдены».

## Проверка устойчивости

В `tests/fixtures/orders-broken.json` — валидный заказ и три битые записи
(пустой `id`, плохая дата, нечисловое количество) плюс заказ в чужой валюте:

```bash
php bin/check-orders.php --orders=tests/fixtures/orders-broken.json \
  --csv=output/broken.csv --txt=output/broken.txt --log=output/broken.log
```

Скрипт завершается с кодом 1, в логе три `ERROR` с причинами, в отчёте —
строки `INVALID_RECORD`, валидные заказы обработаны.

## Ограничения и что дальше

* HTTP-источник читает одну страницу: для реального API нужны пагинация,
  авторизация и ретраи.
* Деньги считаются во `float`; для продакшена — целые копейки или `decimal`.
* Проверяется только валюта и цена; НДС, единицы измерения и кратность
  упаковки не сверяются.
* Статусы, кроме `cancelled`, обрабатываются одинаково: `new` и `confirmed`
  оба идут в 1С.
