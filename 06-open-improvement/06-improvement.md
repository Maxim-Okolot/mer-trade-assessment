# 06. Мониторинг расхождений заказов с 1С: замечать до передачи, а не после жалобы

## Проблема

Цены и остатки на сайте и маркетплейсах расходятся с 1С, а заказы уходят
в 1С без проверки. Расхождения всплывают поздно: менеджер замечает странную
цену при звонке клиента, бухгалтерия — при сверке, поддержка — когда заказ
«не прошёл». Разбор каждый раз ручной: выгрузить заказы, выгрузить
номенклатуру, сравнить в Excel, найти виноватого.

На данных задания 01 это не теория: **14 расхождений по 13 заказам из 31**.
Четыре блокирующих (нет артикула `TS-1099`, `TS-2001`, нет цены, пустой
заказ) и десять предупреждений: `TS-1004` — 1 150 против 1 250 в 1С (−8 %),
`TS-1030` — 340 против 315, `TS-1012` — 7 шт. при остатке 5, по `TS-1025`
суммарно нужно 5 при остатке 4.

Страдают: менеджеры (согласование цен), бухгалтерия (сверка не сходится),
поддержка (разбор постфактум), клиенты (заказ пересчитывают или отменяют).
Ручная сверка — 2–3 часа в неделю, и всё равно выборочная.

## Решение: ежечасная сверка с памятью

1. **Запуск.** Раз в час (и обязательно перед выгрузкой в 1С) скрипт читает
   заказы и выгрузку номенклатуры 1С и прогоняет сверку тем же движком, что
   в задании 01. Источник заказов — файл или API, номенклатура — CSV из 1С.
2. **Отпечаток.** Каждое расхождение получает стабильный ключ
   «заказ + артикул + код проблемы» (`MP-24002|TS-1007|PRICE_MISMATCH`).
   Сообщение и цифры могут меняться — ключ остаётся.
3. **Память.** Результат сохраняется в снимок (`state.json`): что найдено,
   когда впервые, сколько висит. Это и есть «до/после».
4. **Диф.** Следующий запуск сравнивает снимки и делит расхождения на
   **новые**, **изменившиеся** (поменялась цена/остаток) и **исправленные**.
5. **Алерт.** В чат уходит только новое и изменившееся — по одной строке
   на заказ: заказ, артикул, цена в заказе и в 1С, остаток, что делать.
   Исправления попадают в дайджест, а не в чат.
6. **Первый запуск — базовая линия.** Все текущие расхождения записываются
   без алертов, чтобы не было шторма. Отменённые заказы и дубли выгрузки
   в алерты не попадают — это шум, а не расхождение цен.
7. **Интеграция.** Блокирующие расхождения не пускают заказ в 1С (или помечают
   его), коммерческие — уходят менеджеру на согласование. Дальше — ежедневный
   дайджест и дашборд: сколько новых, что висит дольше 3 дней, топ SKU.

## Как измеряем эффект

| Метрика | До | Цель после |
|---|---|---|
| Время обнаружения расхождения | 1–3 дня (жалоба/сверка) | ≤ 1 часа |
| Доля заказов, проверенных до передачи в 1С | 0 % | 100 % |
| Ручная сверка | 2–3 ч в неделю | 15–20 мин (разбор алертов) |
| Повторные расхождения по тем же SKU | не считались | −50 % за месяц |
| Ложные срабатывания | — | < 5 % |

Замер: по снимкам `state.json` видно, сколько расхождений новых за день,
сколько исправлено и сколько висит; до внедрения берём две недели ручной
сверки из почты и Excel.

## План внедрения

- **День 1.** Прогон на текущих выгрузках, базовая линия (14 расхождений
  по 13 заказам), ручная проверка, что в отчёт попадает всё, что ловит
  человек. Снимок состояния — файл.
- **Неделя 1.** Cron раз в час, хранение снимка, алерты в корпоративный чат,
  дедупликация, неделя dry-run (алерты только мне), ежедневный дайджест,
  настройка порога по цене.
- **Неделя 2.** Блокировка передачи блокирующих расхождений в модуле обмена,
  дашборд (новые/исправленные/висящие), отчёт по топ-SKU, разбор ложных
  срабатываний, регламент для менеджеров.

## Риски и снижение

| Риск | Что делаем |
|---|---|
| Шторм алертов на первом запуске | первый запуск — базовая линия без уведомлений |
| Устаревшая выгрузка 1С | проверка свежести файла: старше 24 часов — отдельный алерт |
| Легитимная акция выглядит как расхождение | порог по сумме/проценту, список исключений, подтверждение менеджером |
| Потеря `state.json` | история в БД или бэкап; при потере — разовый baseline |
| Дубли и отмены заказов шумят | исключены из алертов, остаются только в полном отчёте |
| Алерт-шторм по одному SKU | группировка по артикулу, один алерт на проблему |

## Где помогут ИИ

- **Дайджест.** Модель сворачивает 13 изменений в три строки: «две цены
  выросли, один остаток ушёл в минус, один заказ без артикула».
- **Классификация причины.** По истории (акция, смена прайса, ошибка
  округления) модель подсказывает вероятную причину и кому адресовать.
- **Черновик сообщения** менеджеру или категорийному: без технического
  жаргона, с конкретным заказом и суммой.
- **Ограничение:** ИИ не в критическом пути. Сверка, диф и алерты работают
  на правилах; если модель недоступна, ничего не ломается.

## Прототип

`prototype/monitor-discrepancies.php` — рабочий макет на PHP 8.1+.
Переиспользует движок сверки из задания 01 и его данные (31 заказ,
40 строк номенклатуры), хранит снимок и показывает диф.

```powershell
# из папки 06-open-improvement
# первый запуск: базовая линия, без алертов (снимок в var\monitor-state.json)
php prototype\monitor-discrepancies.php --baseline

# следующий запуск по новому срезу: только новые и исправленные
php prototype\monitor-discrepancies.php --orders=prototype\fixtures\orders-next.json
```

Снимок и лог по умолчанию пишутся в `var\` в корне репозитория (каталог
исключён из git). Если писать туда нельзя, лог уходит в системный `NUL`,
а запуск продолжается — мониторинг не должен падать из-за лога.

В `fixtures/orders-next.json` исправлены два расхождения (цена `TS-1004`
и цена `TS-1003`) и добавлено одно новое (`TS-1007`, 2,90 против 2,40).
Прототип показывает: **новых — 1, исправлено — 2**, код возврата `2`.
`--json` отдаёт то же в виде payload для вебхука, `--help` — параметры.
Пример вывода — `prototype/output/example-alert.txt`.

На стенде меняются только источник (запрос к API маркетплейса вместо файла)
и приёмник (webhook в чат вместо консоли); правила и снимок остаются.
